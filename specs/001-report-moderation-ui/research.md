# Research: Модерация доносов (UI)

Все решения следуют `practices/practice_05/contract.md`. Пункты, которых нет в контракте, помечены
как «требует согласования».

## R1. Передача ошибок полей в шаблон формы

- **Decision**: маршрут `POST /report` при ошибках валидации сохраняет введённые значения и список
  ошибок, затем рендерит `index.html` с HTTP 422. Ошибки передаются словарём `field_errors`
  (`{"name": "NAME_REQUIRED"}`), тексты подставляются в шаблоне через общий словарь.
- **Rationale**: контракт требует HTML-перерисовку с тем же HTTP-кодом. `fields[]` из JSON логика
  отдаёт только API-клиентам.
- **Alternatives considered**: редирект с `flash` (отвергнут: не сохраняет значения полей и не даёт
  ошибку под конкретным полем); `session` (отвергнут: лишнее состояние).

## R2. Сохранение введённых значений

- **Decision**: при 422, 409 и 500 шаблон `index.html` получает значения из `request.form` (`name`,
  `group`, `details`, `vibe_level`) и выводит их в `value` и `textarea`. Значения проходят через
  автоэкранирование Jinja2.
- **Rationale**: контракт: «Введённые значения UI берёт из `request.form` при перерисовке формы».
- **Alternatives considered**: хранение в сессии (отвергнут: не требуется).

## R3. Словарь «код → текст»

- **Decision**: один словарь `ERROR_TEXTS` в `server.py`, содержащий все тексты из контракта
  (раздел «Тексты для UI»). Шаблоны получают готовый текст через передачу словаря или через фильтр.
- **Rationale**: тексты заданы в одном месте; шаблоны без логики. Конституция: логика в `server.py`.
- **Alternatives considered**: словарь в шаблоне (отвергнут: шаблоны должны быть без логики);
  отдельный модуль `texts.py` (допустим, но лишний файл для шести текстов).

## R4. `return_query` и белый список

- **Decision**: в `reports.html` каждая форма статуса содержит скрытое поле `return_query`, значение
  которого строится из текущих фильтров через `{{ filters | urlencode }}`-подобную конструкцию (Jinja
  `urlencode` принимает словарь). Логика принимает только `status`, `vibe_level`, `group`, `q` и
  добавляет их к редиректу `303`.
- **Rationale**: контракт фиксирует `return_query` и белый список. Шаблон не решает, что разрешено.
- **Alternatives considered**: передавать фильтры отдельными скрытыми полями (отвергнут: логика всё
  равно должна проверять их по белому списку, а `return_query` уже это описывает).
- **Примечание**: Jinja `urlencode` кодирует значения; логика должна декодировать их штатным разбором
  query-строки.

## R5. Экраны «Донос не найден» и «Страница не найдена.»

- **Decision**: требует согласования. Предложение: новый шаблон `not_found.html` с параметрами
  `title`, `message` и ссылками. Для неизвестного пути `/foo` тот же шаблон с другим текстом.
- **Rationale**: два экрана различаются текстом и ссылками, но структура одна.
- **Alternatives considered**: без нового шаблона, через условия в `base.html` (отвергнут: усложняет общий
  шаблон); два отдельных шаблона (отвергнут: дублирование).
- **Статус**: открыт; до согласования использовать один шаблон-заглушку (предложение выше).
- Для 400 «Некорректный запрос.» и 500 при смене статуса нужен отдельный шаблон `error.html`
  (предложение, требует согласования): он выводит один текст и ссылку на `/reports`.

## R6. Кнопка текущего статуса и `select`

- **Decision**: в `reports.html` кнопка «Подтвердить» получает `disabled`, если `r.status == 'confirmed'`,
  «Отклонить» — если `r.status == 'rejected'`. В `select` выбранный вариант помечается через `selected`
  по значению `filters.status` и `filters.vibe_level`.
- **Rationale**: контракт требует `disabled` без JavaScript; текущий шаблон уже использует `selected`.
- **Alternatives considered**: скрытие кнопки (отвергнут: контракт требует `disabled`).

## Требует подтверждения от логики

- Декодирование `return_query` и отсутствие лишних параметров в редиректе (R4).
- Передача `field_errors` и значений в шаблон при 422 (R1, R2). Контракт описывает поведение, а не
  имена переменных шаблона.
