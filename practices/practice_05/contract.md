# Контракт: Модерация доносов (UI ⇄ Логика)

Дата: 2026-10-22

Статус: согласовано для реализации следующего этапа. Документ фиксирует единый контракт между UI и логикой с учётом текущего состояния проекта практики 4.

## Контекст и базовая платформа

- Базовый проект (practice_04) — Flask без БД, данные в памяти процесса.
- Уже реализованы маршруты: `GET /`, `POST /report`, `GET /thanks`, `GET /reports`, а также `GET /reports/export` (расширение, присутствует в коде).
- Формы и страницы — серверный рендеринг (HTML), без JavaScript.

## Единые определения

- Статусы записей: коды `new`, `confirmed`, `rejected`. Отображаемые подписи задаёт UI: «На рассмотрении», «Подтверждён», «Отклонён».
- Поля записи: `id`, `name`, `group`, `details`, `vibe_level`, `status`, `created_at`.
- Допустимые значения `vibe_level`: `low`, `medium` (по умолчанию), `high`.

## Поля форм и ограничения

- Форма создания (`POST /report`) передаёт поля: `name` (обязательно), `group` (необязательно), `details` (обязательно), `vibe_level` (select: low/medium/high; по умолчанию medium).
- Ограничения длины, применяемые логикой:
  - `name`: 2–60 символов (после обрезки по краям).
  - `group`: 0–20 символов (после обрезки по краям).
  - `details`: 10–1000 символов (после обрезки по краям).
- UI добавляет подсказки в виде HTML-атрибутов: `maxlength` для `name` (60) и `group` (20). Для `details` `maxlength` не используется, окончательную проверку выполняет сервер.

## Ошибки и формат ответов

Единый набор кодов ошибок и статусов HTTP:

- Верхний уровень:
  - `VALIDATION_FAILED` (422) — ошибки полей при создании.
  - `DUPLICATE` (409) — попытка создать дубликат.
  - `INVALID_STATUS` (400) — неизвестный статус, целевой `new`, неверный `status` в фильтре.
  - `VIBE_INVALID` (400) — неверный `vibe_level` в фильтре или форме.
  - `INVALID_FORMAT` (400) — неверный формат экспорта.
  - `NOT_FOUND` (404) — запись не найдена или номер некорректен.
  - `INTERNAL_ERROR` (500) — непредвиденная ошибка.
- Ошибки полей (внутри `fields[].code` при `VALIDATION_FAILED`): `NAME_REQUIRED`, `NAME_LENGTH`, `GROUP_LENGTH`, `DETAILS_REQUIRED`, `DETAILS_LENGTH`, `VIBE_INVALID`.

Представления:

- Выбор представления — по заголовку `Accept` запроса (решение пользователя, 2026-10-22):
  - Если `Accept` содержит `application/json`, ответ JSON (API).
  - Иначе ответ HTML (браузер). Это касается `POST /report`, `GET /reports`, `POST /reports/{id}/status`, `GET /reports/export` (ошибки), `GET /thanks`, `GET /reports/{id}`.
  - Заголовок `Accept` не задан или `*/*` — HTML.
- Браузерные маршруты возвращают HTML-страницы с теми же кодами HTTP (422/409/404/500). Введённые значения UI берёт из `request.form` при перерисовке формы.
- API-маршруты возвращают JSON:
  - `{"error": {"code": "<КОД>"}}`
  - Для 422: `{"error": {"code": "VALIDATION_FAILED", "fields": [{"field": "name", "code": "NAME_LENGTH"}, ...]}}`

Тексты для UI (сопоставляются по кодам):

- `NAME_REQUIRED` → «Укажите имя студента.»
- `DETAILS_REQUIRED` → «Опишите ситуацию.»
- `NAME_LENGTH` → «Имя студента: от 2 до 60 символов.»
- `GROUP_LENGTH` → «Группа: не больше 20 символов.»
- `DETAILS_LENGTH` → «Описание: от 10 до 1000 символов.»
- `VIBE_INVALID` → «Выберите уровень из списка.»
- `DUPLICATE` → «Такой донос уже отправлен. Измените данные и отправьте снова.»
- `INTERNAL_ERROR` → «Не удалось отправить донос. Попробуйте ещё раз.»
- 400 для подмены параметров (`INVALID_STATUS`, `VIBE_INVALID`, `INVALID_FORMAT`) → общая страница «Некорректный запрос.»
- `NOT_FOUND` в маршрутах, принимающих номер → страница «Донос не найден» (см. ниже). Для неизвестного пути (`/foo`) — отдельная страница «Страница не найдена.»

## Дублирование

- Ключ дубликата: пара (`name`, `details`), нормализованная обрезкой краёв, склейкой последовательностей пробельных символов в один пробел и `casefold` по Unicode.
- Включает записи всех статусов, включая `rejected`. Повторная отправка ранее отклонённого доноса считается дубликатом.
- Проверяется только при создании. Атомарность обеспечивается сервером.

## Смена статуса и кнопки в UI

- Допустимые переходы: `new → confirmed|rejected`; между `confirmed` и `rejected` — свободно; возврат в `new` запрещён.
- Передача текущего статуса (no-op) возвращает успех 303; UI выводит нейтральный текст: «Статус доноса №{номер}: «{статус}».».
- Кнопка текущего статуса отображается с атрибутом `disabled` в UI (без JS), чтобы избежать лишних no-op.

## Фильтры списка и счётчики

- `GET /reports` принимает параметры (AND):
  - `status`: `all|new|confirmed|rejected`; отсутствует/пусто/`all` — не фильтровать.
  - `vibe_level`: `any|low|medium|high`; отсутствует/пусто/`any` — не фильтровать.
  - `group`: непустая строка — подстрока без учёта регистра в поле `group`.
  - `q`: непустая строка — подстрока без учёта регистра в `name` или `details`.
- Неверные значения `status` или `vibe_level` → 400 (`INVALID_STATUS`/`VIBE_INVALID`).
- Счётчики: `total` — все записи; `shown` — после фильтра; `by_status` — количества по всем статусам; инвариант `new + confirmed + rejected = total`.

## Экспорт

- Маршрут: `GET /reports/export?format=csv|json`.
- Экспорт применяет те же фильтры, что и список (`status`, `vibe_level`, `group`, `q`).
- CSV:
  - Заголовок: `id,name,group,vibe_level,status,created_at,details`.
  - Порядок строк: по `id` по возрастанию.
  - UTF-8 с BOM; `Content-Type: text/csv; charset=utf-8`; `Content-Disposition: attachment; filename=reports.csv`.
  - RFC 4180 кавычки и экранирование.
  - Защита от формульной инъекции: значения, начинающиеся с `=`, `+`, `-`, `@`, табуляции или `\r`, получают префикс `'`.
- JSON:
  - Массив записей с полями из раздела «Единые определения».
  - `Content-Type: application/json; charset=utf-8`; `Content-Disposition: attachment; filename=reports.json`.

## Маршруты и ответы

Таблица согласованных маршрутов и представлений:

- `GET /` — HTML форма.
- `POST /report` —
  - Успех: 302 → `Location: /thanks?id={id}`.
  - Ошибки: 422 `VALIDATION_FAILED` (HTML перерисовка для браузера, JSON для API), 409 `DUPLICATE`, 500 `INTERNAL_ERROR`.
- `GET /thanks` —
  - 200: `{id}` или `{id: null}` при отсутствии параметра; HTML-страница для браузера.
  - 404: `NOT_FOUND` при несуществующем или некорректном `id`.
- `GET /reports` —
  - 200: список, счётчики, фильтры; HTML для браузера, структура данных для API.
  - 400: `INVALID_STATUS`, `VIBE_INVALID`.
- `POST /reports/{id}/status` —
  - Успех: 303 → `Location: /reports?changed_id={id}&changed_to={status}`.
  - Сохранение текущих фильтров: UI передаёт скрытое поле `return_query`; логика добавляет к редиректу только параметры из белого списка (`status`, `vibe_level`, `group`, `q`).
  - Ошибки: 400 `INVALID_STATUS`, 404 `NOT_FOUND`, 500 `INTERNAL_ERROR`.
- `GET /reports/{id}` — API возвращает одну запись (JSON, 200); 404 `NOT_FOUND` при отсутствии; отдельная HTML-страница UI не реализуется.
- `GET /reports/export` — экспорт CSV/JSON с фильтрами; 400 `INVALID_FORMAT`, `INVALID_STATUS`, `VIBE_INVALID`.
- Неизвестный путь — 404; для браузера отдельная страница «Страница не найдена.».

Примечание по совместимости с практикой 4: расширенные маршруты (`/reports/{id}`, `/reports/{id}/status`) согласованы в этом контракте для реализации следующего этапа. Браузерные представления не меняют коды HTTP.

## Страницы UI

- Форма (`/`): ошибки под полями, блоки для `DUPLICATE` и `INTERNAL_ERROR`, сохранение введённых значений при перерисовке, успех → редирект на `/thanks?id={id}`.
- Благодарность (`/thanks`): отображает номер; при отсутствии — текст-заглушка; при несуществующем номере — страница «Донос не найден».
- Список (`/reports`): фильтр по статусу и уровню, поля `group` и `q`, счётчик «Показано X из Y», пустой список и пустой результат фильтра, кнопки «Подтвердить»/«Отклонить» с `disabled` на текущем статусе, нейтральный текст после действия.
- Донос не найден: заголовок «Донос не найден», текст без номера если `id` некорректный (не положительное целое), ссылки «Вернуться к списку доносов» и «Отправить донос».
- Страница «Страница не найдена.» для неизвестных путей.

## Безопасность и доступ

- Контроль доступа отсутствует; `GET /reports` и `GET /reports/{id}` возвращают `details` любому пользователю. Для учебного проекта допустимо. На проде потребуются ограничения.
- Экранирование всех отображаемых значений на стороне UI обязательно.
