## Исходное состояние

- Заявки хранятся в списке в памяти процесса. Каждая запись содержит поля `name`, `group`, `details`,
  `vibe_level`. Полей `id`, `status`, `created_at` нет.
- Текущая валидация: проверяются только `name` и `details` на непустоту после обрезки пробелов.
  Если `vibe_level` не передан, используется `medium`.
- `GET /reports` фильтрует по `vibe_level` (неизвестное значение игнорируется), `group` и `q`.
- `GET /reports/export` экспортирует все записи в CSV или JSON без фильтров; неизвестный формат даёт 400.
- Успешная отправка `POST /report` даёт 302 на `/thanks` без номера.

Всё, что меняется относительно этого состояния, отмечено в тексте как «изменение».

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Создание доноса с валидацией и защитой от дублей (Priority: P1)

Логика принимает донос, проверяет поля и отклоняет некорректные данные или дубликаты. Принятый донос
получает уникальный номер и статус `new`.

**Why this priority**: без корректного создания не работает ни одна часть модерации.

**Independent Test**: отправить `POST /report` с разными наборами полей и проверить код ответа,
содержимое хранилища и список ошибок.

**Acceptance Scenarios**:

1. **Given** хранилище пусто, **When** приходит `name="Иван"`, `details="Опоздал на пару сегодня"`,
   `group` и `vibe_level` не переданы, **Then** создаётся запись с `id=1`, `status=new`,
   `vibe_level=medium`, `group=""`, заполненным `created_at`; ответ 302 с `Location: /thanks?id=1`.
2. **Given** хранилище пусто, **When** приходит `name="И"`, **Then** ответ 422 с ошибкой `NAME_LENGTH`
   для поля `name`, запись не создаётся.
3. **Given** хранилище пусто, **When** `name` и `details` пусты, **Then** ответ 422 с двумя ошибками
   (`NAME_REQUIRED` для `name`, `DETAILS_REQUIRED` для `details`) одновременно.
4. **Given** есть запись `name="Иван Петров"`, `details="Опоздал на пару"`, **When** приходит
   `name="  иван   ПЕТРОВ "`, `details="опоздал на пару"`, **Then** ответ 409 `DUPLICATE`, новая запись
   не создаётся.
5. **Given** есть запись `name="Иван Петров"`, `details="Опоздал на пару"`, **When** приходит та же
   `name` с другим `details`, **Then** запись создаётся.
6. **Given** `vibe_level="extreme"`, **When** отправляется форма, **Then** ответ 422 с ошибкой
   `VIBE_INVALID` для поля `vibe_level`.
7. **Given** два одинаковых запроса приходят одновременно, **When** обрабатываются, **Then** ровно один
   создаёт запись (302), второй получает 409 `DUPLICATE`.

### User Story 2 - Смена статуса доноса (Priority: P1)

Модератор переводит донос в `confirmed` или `rejected`. Статус можно менять несколько раз. Вернуть
статус `new` нельзя.

**Why this priority**: смена статуса — основное действие модерации.

**Independent Test**: создать донос, выполнить последовательность смен статуса, проверить ответы и
значения в хранилище.

**Acceptance Scenarios**:

1. **Given** донос `id=1` со статусом `new`, **When** `POST /reports/1/status` с `status=confirmed`,
   **Then** статус становится `confirmed`; ответ 303 с `Location: /reports?updated=1&status=confirmed`.
2. **Given** донос со статусом `confirmed`, **When** приходит `status=rejected`, **Then** статус
   становится `rejected`.
3. **Given** донос со статусом `rejected`, **When** приходит `status=confirmed`, **Then** статус
   становится `confirmed`.
4. **Given** донос со статусом `confirmed`, **When** приходит `status=confirmed`, **Then** статус не
   меняется, ответ 303 как при успехе.
5. **Given** любой донос, **When** приходит `status=new`, **Then** ответ 400 `INVALID_STATUS`, статус не
   меняется.
6. **Given** любой донос, **When** приходит `status=approved` (неизвестное значение), **Then** ответ 400
   `INVALID_STATUS`.
7. **Given** донос с номером 5 не существует, **When** приходит `POST /reports/5/status` с
   `status=confirmed`, **Then** ответ 404 `NOT_FOUND`.
8. **Given** донос сменил статус, **When** статус изменён, **Then** `created_at`, `name`, `group`,
   `details`, `vibe_level` и `id` не меняются.

### User Story 3 - Фильтрация списка и счётчики (Priority: P2)

Модератор видит список, отфильтрованный по статусу, уровню, группе и строке поиска одновременно, и
счётчики по всей базе.

**Why this priority**: нужна для работы с большим количеством доносов, но без неё модерация работает.

**Independent Test**: создать набор доносов с разными значениями полей, применить комбинации фильтров
и сравнить результат и счётчики с ожидаемыми.

**Acceptance Scenarios**:

1. **Given** 3 доноса (2 `new`, 1 `confirmed`), **When** `GET /reports` без параметров, **Then** в ответе
   3 записи, `total=3`, `shown=3`, `by_status={new: 2, confirmed: 1, rejected: 0}`.
2. **Given** те же доносы, **When** `GET /reports?status=confirmed`, **Then** возвращается 1 запись,
   `total=3`, `shown=1`, `by_status` не изменился.
3. **Given** доносы с разными `vibe_level`, **When** `GET /reports?status=new&vibe_level=high&group=it`,
   **Then** возвращаются только записи, удовлетворяющие всем трём условиям (AND).
4. **Given** фильтры, которые не совпадают ни с одной записью, **When** запрос выполняется, **Then**
   ответ 200, `reports=[]`, `shown=0`, `total` содержит общее количество.
5. **Given** пустое хранилище, **When** `GET /reports`, **Then** ответ 200, `reports=[]`, `total=0`,
   `shown=0`, `by_status` содержит нули.
6. **Given** `GET /reports?status=pending`, **Then** ответ 400 `INVALID_STATUS`.

### User Story 4 - Экспорт (Priority: P2)

Модератор выгружает записи в CSV или JSON. Экспорт применяет те же фильтры, что и список.

**Why this priority**: нужен для внешней обработки, но не блокирует модерацию.

**Independent Test**: выполнить экспорт в обоих форматах с фильтром и без него, проверить заголовки,
кодировку и состав полей.

**Acceptance Scenarios**:

1. **Given** 2 доноса, **When** `GET /reports/export` без параметров, **Then** ответ 200, CSV с
   заголовком и 2 строками, записи в порядке `id` по возрастанию.
2. **Given** 2 доноса, **When** `GET /reports/export?format=json`, **Then** ответ 200, JSON-массив из
   2 объектов с полями `id`, `name`, `group`, `vibe_level`, `status`, `created_at`, `details`.
3. **Given** доносы разных статусов, **When** `GET /reports/export?format=csv&status=rejected`, **Then**
   в файле только отклонённые.
4. **Given** пустое хранилище, **When** экспорт в CSV, **Then** файл содержит только строку заголовка;
   в JSON `[]`.
5. **Given** `GET /reports/export?format=xml`, **Then** ответ 400 `INVALID_FORMAT`.

### User Story 5 - Просмотр одного доноса и обработка несуществующего номера (Priority: P3)

Любой маршрут, принимающий номер доноса, одинаково обрабатывает несуществующий или некорректный номер.

**Why this priority**: крайний случай, но он должен давать предсказуемый ответ.

**Independent Test**: запросить номера, которых нет, и номера неверного формата.

**Acceptance Scenarios**:

1. **Given** донос `id=1`, **When** `GET /reports/1`, **Then** ответ 200 с полями записи.
2. **Given** нет доноса `id=99`, **When** `GET /reports/99`, **Then** ответ 404 `NOT_FOUND`.
3. **Given** номер не является положительным целым (`abc`, `0`, `-1`), **When** `GET /reports/abc`,
   **Then** ответ 404 `NOT_FOUND`.
4. **Given** `GET /thanks` без параметра `id`, **Then** ответ 200 с `id=null`.
5. **Given** `GET /thanks?id=99` для несуществующего доноса, **Then** ответ 404 `NOT_FOUND`.

### Edge Cases

- Граница `name`: 1 символ → ошибка; 2 и 60 символов → допустимо; 61 символ → ошибка.
- Граница `group`: 0 символов → допустимо; 20 → допустимо; 21 → ошибка `GROUP_LENGTH`.
- Граница `details`: 9 символов → ошибка; 10 и 1000 → допустимо; 1001 → ошибка `DETAILS_LENGTH`.
- Строка из одних пробелов или переносов трактуется как пустая: `NAME_REQUIRED` или `DETAILS_REQUIRED`.
- Перед проверкой длины значения обрезаются по краям. Внутренние пробелы и переносы строк сохраняются.
- Длина считается в символах Unicode (кодовых точках). `\r\n` считается одним переносом строки.
- Одновременное наличие ошибок в нескольких полях: возвращаются все ошибки сразу, дубликат не проверяется.
- Значения, содержащие HTML (`<b>текст</b>`), сохраняются как введены. Экранирование выполняется при выводе.
- `vibe_level` приводится к нижнему регистру до проверки: `HIGH` принимается как `high`.
- Пустой `vibe_level` трактуется как отсутствующий и даёт `medium`.
- Ё и Е считаются разными символами при сравнении дубликатов (см. «Защита от дублей»).
- Перезапуск процесса очищает хранилище; `id` начинается с 1 заново. Номер, выданный до перезапуска,
  после перезапуска может указывать на другой донос или на отсутствующий. Это ожидаемое поведение.
- Номер доноса не переиспользуется в пределах одного запуска, даже если запись будет удалена (удаление
  в этой фиче не предусмотрено).

## Requirements *(mandatory)*

### Модель данных

Каждая запись содержит:

| Поле | Тип | Правила | Значение по умолчанию |
|------|-----|---------|----------------------|
| `id` | целое | положительное, уникальное, выдаётся по возрастанию, не переиспользуется в пределах запуска | назначается при создании |
| `name` | строка | обязательное; длина 2–60 символов после обрезки | — |
| `group` | строка | необязательное; длина 0–20 символов после обрезки | `""` |
| `details` | строка | обязательное; длина 10–1000 символов после обрезки | — |
| `vibe_level` | перечисление | `low`, `medium`, `high` | `medium` |
| `status` | перечисление | `new`, `confirmed`, `rejected` | `new` |
| `created_at` | дата-время | UTC, формат `YYYY-MM-DDTHH:MM:SSZ`; назначается один раз при создании и не меняется | назначается при создании |

Изменение: поля `id`, `status`, `created_at` добавляются ко всем записям, включая уже существующие
(при старте хранилище пустое, миграции не требуется).

### Правила валидации

Порядок: обрезка пробелов → проверка → проверка дубликата (только если ошибок валидации нет) → сохранение.

| Поле | Правило | Код ошибки |
|------|---------|------------|
| `name` | пусто после обрезки | `NAME_REQUIRED` |
| `name` | длина вне 2–60 | `NAME_LENGTH` |
| `group` | длина больше 20 | `GROUP_LENGTH` |
| `details` | пусто после обрезки | `DETAILS_REQUIRED` |
| `details` | длина вне 10–1000 | `DETAILS_LENGTH` |
| `vibe_level` | значение не из `low`, `medium`, `high` (после приведения к нижнему регистру) | `VIBE_INVALID` |

Изменение: текущая проверка длин и `vibe_level` отсутствует; добавляются все правила выше.

Ошибки возвращаются списком `fields`: по одной записи на каждое неверное поле.

### Защита от дублей

**Ключ дубликата** — пара (`name`, `details`), нормализованная так:
1. Обрезка пробелов по краям.
2. Любая последовательность пробельных символов (пробел, табуляция, перенос строки) заменяется одним пробелом.
3. Приведение к нижнему регистру по правилам Unicode (`casefold`). Например, `ß` и `ss` совпадают.

Поля `group` и `vibe_level` в ключ не входят.

**Область проверки**: все записи в хранилище, независимо от статуса (включая `rejected`). Повторная
отправка уже отклонённого доноса тоже считается дубликатом.

**Когда проверяется**: только при создании. Смена статуса дубликаты не создаёт.

**Атомарность**: проверка и сохранение выполняются как одна операция. Два одинаковых запроса не могут
оба создать запись.

**Результат**: 409 `DUPLICATE`. Запись не создаётся, номер существующего доноса не возвращается.

### Смена статуса

Допустимые переходы:

| Из \ В | `new` | `confirmed` | `rejected` |
|--------|-------|-------------|------------|
| `new` | нет | да | да |
| `confirmed` | нет | no-op | да |
| `rejected` | нет | да | no-op |

- Целевой статус `new` запрещён из любого состояния: 400 `INVALID_STATUS`.
- Передача текущего статуса (no-op, в таблице) возвращает успех без изменений.
- Неизвестное значение статуса: 400 `INVALID_STATUS`.
- Порядок проверок: сначала значение статуса (400), затем существование доноса (404).
- При успехе меняется только `status`.

Изменение: поля `status` до этой фичи не существовало.

### Фильтрация списка

Параметры `GET /reports` (все опциональны, объединяются через AND):

| Параметр | Значения | Поведение |
|----------|----------|-----------|
| `status` | `all`, `new`, `confirmed`, `rejected` | отсутствует, пусто или `all` — не фильтровать; иное — точное совпадение |
| `vibe_level` | `any`, `low`, `medium`, `high` | отсутствует, пусто или `any` — не фильтровать; иное — точное совпадение |
| `group` | строка | отсутствует или пусто — не фильтровать; иначе подстрока без учёта регистра, после обрезки пробелов |
| `q` | строка | отсутствует или пусто — не фильтровать; иначе подстрока в `name` или `details` без учёта регистра, после обрезки пробелов |

- Записи в ответе идут по `id` по возрастанию.
- Неверное значение `status` или `vibe_level` → 400 (`INVALID_STATUS` или `VIBE_INVALID`).

Изменение: неизвестное значение `vibe_level` раньше игнорировалось (трактовалось как `any`). Теперь
возвращается 400.

### Счётчики

Все три счётчика вычисляются при каждом запросе:

- `total` — количество всех записей. Фильтры не влияют.
- `shown` — количество записей, попавших в ответ после фильтров.
- `by_status` — объект `{new, confirmed, rejected}` с количеством записей каждого статуса по всему
  хранилищу. Фильтры не влияют. Нулевые значения присутствуют.

Инвариант: `new + confirmed + rejected = total`.

### Маршруты

Все ошибки возвращаются в одном формате (см. «Формат ошибок»).

| Метод и путь | Вход | Успех | Ошибки |
|--------------|------|-------|--------|
| `GET /` | — | без изменений | — |
| `POST /report` | поля формы `name`, `group`, `details`, `vibe_level` | 302, `Location: /thanks?id={id}` | 422 `VALIDATION_FAILED` с `fields`; 409 `DUPLICATE`; 500 `INTERNAL_ERROR` |
| `GET /thanks` | query `id` (необязательный) | 200, `{id}` или `{id: null}` при отсутствии параметра | 404 `NOT_FOUND` если `id` не существует или не является положительным целым |
| `GET /reports` | query: `status`, `vibe_level`, `group`, `q` | 200, `{reports, total, shown, by_status}` | 400 `INVALID_STATUS`, 400 `VIBE_INVALID` |
| `GET /reports/{id}` | путь `id` | 200, одна запись | 404 `NOT_FOUND` |
| `POST /reports/{id}/status` | поле `status` (`confirmed` или `rejected`) | 303, `Location: /reports?updated={id}&status={status}` | 400 `INVALID_STATUS`; 404 `NOT_FOUND` |
| `GET /reports/export` | query: `format` (`csv` по умолчанию, `json`), плюс фильтры `status`, `vibe_level`, `group`, `q` | 200, файл | 400 `INVALID_FORMAT`; 400 `INVALID_STATUS`; 400 `VIBE_INVALID` |

Общие правила:
- Метод, отличный от указанного для пути: 405.
- Неизвестный путь: 404.
- Вход, не описанный в таблице, игнорируется.

Формат записи (в `GET /reports`, `GET /reports/{id}` и экспорте JSON):
`{"id": int, "name": str, "group": str, "details": str, "vibe_level": str, "status": str, "created_at": str}`.

Изменение: маршруты `GET /reports/{id}`, `POST /reports/{id}/status`, `GET /reports/export` с фильтрами —
новые или расширенные. Согласование контракта см. в «Открытые вопросы».

### Формат ошибок

Каждая ошибка возвращается в виде:

```
{"error": {"code": "<КОД>"}}
```

Для `VALIDATION_FAILED` добавляется список полей:

```
{"error": {"code": "VALIDATION_FAILED", "fields": [{"field": "name", "code": "NAME_LENGTH"}]}}
```

Тексты сообщений в ответах логики не возвращаются. Сопоставление кодов с текстами — задача UI.

**Таблица кодов**:

| Код | HTTP | Когда |
|-----|------|-------|
| `VALIDATION_FAILED` | 422 | ошибки полей при создании; подробности в `fields` |
| `NAME_REQUIRED`, `NAME_LENGTH`, `GROUP_LENGTH`, `DETAILS_REQUIRED`, `DETAILS_LENGTH`, `VIBE_INVALID` | (внутри 422 или 400) | коды полей |
| `DUPLICATE` | 409 | создание дубликата |
| `INVALID_STATUS` | 400 | неизвестный статус, `new` в качестве целевого, неверный `status` в фильтре |
| `VIBE_INVALID` | 400 | неверный `vibe_level` в фильтре |
| `INVALID_FORMAT` | 400 | неизвестный `format` при экспорте |
| `NOT_FOUND` | 404 | донос не найден или номер некорректен |
| `INTERNAL_ERROR` | 500 | непредвиденная ошибка; хранилище не меняется |

Код `VIBE_INVALID` используется и в поле формы (внутри 422), и в фильтре (400).

### Экспорт

- Маршрут: `GET /reports/export`.
- Фильтры такие же, как у `GET /reports`. Без фильтров экспортируются все записи.
- Порядок: по `id` по возрастанию.

**CSV**:
- Кодировка UTF-8 с BOM. Разделитель `,`. Значения, содержащие `,`, `"` или перенос строки, берутся в
  двойные кавычки (правила RFC 4180).
- Заголовок: `id,name,group,vibe_level,status,created_at,details`.
- Пустой набор: только строка заголовка.
- `Content-Type: text/csv; charset=utf-8`.

## Что я ожидаю от UI

Раздел описывает, что интерфейс отправляет логике и что обязан показать. Тексты экранов и вёрстка
определяются спецификацией UI.

**Что UI отправляет:**
- `POST /report`: поля `name`, `group`, `details`, `vibe_level`. Значения передаются как введены,
  без обрезки и приведения регистра (это делает логика).
- `POST /reports/{id}/status`: поле `status` со значением `confirmed` или `rejected`. Номер доноса
  берётся из пути, а не из тела.
- `GET /thanks`: параметр `id` с номером, полученным после создания.
- `GET /reports`: параметры `status`, `vibe_level`, `group`, `q`. Значения «Все статусы» и «Любой уровень»
  передаются как `all` и `any` либо отсутствуют.
- `GET /reports/export`: параметры `format` и текущие фильтры списка.

**Что UI получает и должен показать:**
- Для `POST /report` при 422: список `fields` с кодом на каждое поле. UI выводит текст рядом с полем.
  Введённые значения UI хранит сам, логика их не возвращает.
- Для `POST /report` при 409: код `DUPLICATE`. UI выводит блок над формой, значения сохраняются.
- Для `POST /report` при 302: переход на `/thanks?id={id}`.
- Для `GET /thanks`: номер `id`, либо `null` при отсутствии параметра, либо 404 для несуществующего.
- Для `GET /reports`: список записей, `total`, `shown`, `by_status`, значения фильтров для отметки в полях.
  UI выводит «Показано {shown} из {total}». Признаки «список пуст» и «фильтр не нашёл доносов» UI
  вычисляет сам: `total = 0` и `shown = 0` при `total > 0`.
- Для `POST /reports/{id}/status` при 303: переход на `/reports?updated={id}&status={status}`. UI выводит
  подтверждение смены статуса.
- Для 404 на любом маршруте, принимающем номер: страница «Донос не найден». Номер берётся из запроса.
- Для 400 `INVALID_STATUS` и `VIBE_INVALID`: UI не показывает их пользователю напрямую, так как значения
  выбираются из списка; ошибка означает подмену параметра.
- Для 400 `INVALID_FORMAT`: UI не предоставляет выбор формата вне списка; ошибка означает подмену параметра.
- Для 500 `INTERNAL_ERROR`: общее сообщение об ошибке, данные не меняются.
- Статус отображается по коду `new`, `confirmed`, `rejected`. Сопоставление кода с подписью делает UI.
- Все значения, которые приходят из логики, выводятся экранированными (включая значения из `name`,
  `group`, `details`).
- UI не вычисляет счётчики, не проверяет длины и дубликаты самостоятельно. Серверные правила
  авторитетны, клиентские ограничения (например, `maxlength`) допустимы только как подсказка.
- UI не отправляет `id`, `status` при создании и `created_at`. Эти поля назначает логика.
- При смене статуса UI не показывает переходы, которых нет в таблице «Смена статуса» (например, в `new`).
  Кнопка «Подтвердить» для уже подтверждённого доноса выполняет no-op; UI может её скрыть или оставить.
