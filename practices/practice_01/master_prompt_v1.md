## Master Prompt v1

### 1. Цель и роль

- **Цель:** на основе `TRAINING_PR.diff` и правил репозитория из `CASE.md` собрать связный комплект SDLC-артефактов Практики 1 (все 11 файлов из таблицы `README.md`) и зафиксировать этот прогон как `P1-02` в `prompts.md`. Не изобретать фактов, которых нет в diff, в `CASE.md` или в самих шаблонах.
- **Роль AI:** технический аналитик и архитектор, который документирует код из diff как продукт «AI-помощник ревьюера PR»: находит расхождения между тем, что реализовано в diff, и правилами `SEC-1`, `API-1`, `REL-1`, `OUT-1`, `SCOPE-1`, `QA-1`, `OBS-1`, и на основе этих расхождений формирует проблему, план, ADR и тесты. AI не пишет и не меняет код в `app/`, не делает approve/merge.

### 2. Входы и источники

- **Обязательный вход:** `TRAINING_PR.diff` — единственный источник фактов о том, что реализовано.
- **Разрешённые файлы и источники:** `CASE.md` (правила SEC-1…OBS-1, задача помощника, хороший/плохой пример комментария), `README.md` (что сдаём и критерии оценки), текущее содержимое всех 11 шаблонов: `context.md`, `problem.md`, `analysis.md`, `product_management.md`, `project_management.md`, `adr.md`, `tests_unit.md`, `tests_integration.md`, `tests_load.md`, `tests_e2e.md`, `prompts.md`.
- **Context Pack (перенести только то, что влияет на этот diff):**
  - Задача помощника: получает diff → возвращает `summary`, ≤3 `risks` (с `file`, `line`, `evidence`, `risk`), `checks`; решение всегда принимает человек.
  - Правила: `SEC-1` (удалять секреты перед отправкой в LLM), `API-1` (413 при diff > 20 000 символов), `REL-1` (timeout 10 сек на вызов LLM), `OUT-1` (формат ответа summary/risks≤3/checks), `SCOPE-1` (сервис только советует, не approve/merge/пишет код), `QA-1` (риск в ответе только если подтверждён строкой diff или правилом), `OBS-1` (лог только request_id, длительность, статус — без содержимого diff/ответа).
  - Явно НЕ переносить в Context Pack: правило `snake_case` для таблиц БД и правило про i18n frontend-строк — не относятся к этому diff.
  - Формат входа/выхода сервиса: вход — сырой diff (str); ожидаемый выход по `OUT-1` — `{summary, risks[≤3], checks}`. В текущем diff `ReviewService.review()` возвращает только `{"comment": answer}` — это расхождение с `OUT-1`, зафиксировать как факт.
  - Хороший/плохой пример комментария — по образцу из `CASE.md`.
  - Ограничение: помощник не пишет код и не действует в GitHub (`SCOPE-1`).

### 3. Задача и артефакты

Заполнить последовательно все 11 файлов, строго по их существующей структуре (не менять заголовки и таблицы, только вписывать содержимое). Для каждого файла — минимум, который должен получиться:

| Файл | Что обязательно должно появиться |
|---|---|
| `context.md` | Таблица AS IS (продукт = AI-ревьюер PR из diff, пользователи = разработчик/ревьюер, текущий процесс = ручное код-ревью, задержка = нет автоматических проверок), Context Pack целиком (см. раздел 2), раздел «Что пока неизвестно» |
| `problem.md` | Пользователь и ситуация; «что происходит сейчас» = перечислить конкретные расхождения diff с SEC-1/API-1/REL-1/OUT-1/QA-1/OBS-1 как факты риска; ≥2 измеримые метрики, привязанные к этим правилам (например: доля ответов с evidence по каждому risk, задержка ответа сервиса, доля diff с секретами, прошедших без редактирования) |
| `analysis.md` | AS IS = как сейчас работает `review()`/`/api/reviews` (без проверок); TO BE = тот же процесс с внедрёнными SEC-1/API-1/REL-1/OUT-1/QA-1/OBS-1; mermaid flowchart; таблица разницы |
| `product_management.md` | Use case (актор = разработчик, триггер = открыт PR / вызван `/api/reviews`); mermaid sequence diagram; user stories: позитивный сценарий (валидный diff → summary/risks/checks) и негативный/граничный (diff > 20000 символов → 413 по API-1) |
| `project_management.md` | Инкременты, по одному на правило или группу правил (например: 1 — SEC-1 редактирование секретов, 2 — API-1 лимит размера, 3 — REL-1 timeout, 4 — OUT-1 структурированный ответ + QA-1 проверка evidence, 5 — OBS-1 логирование), с колонками «делает человек» / «делает AI»; Gantt |
| `adr.md` | Контекст = разрыв diff и правил; Решение = что и как рефакторить в `review_service.py`/`api.py`; Альтернативы (минимум 1, с причиной отказа); Главный риск (например: LLM timeout/недоступность или утечка секрета) и как его проверим; заполненная mermaid-схема |
| `tests_unit.md` | Минимум по одному тесту на SEC-1 (секрет в diff → `[REDACTED]` в prompt), API-1 (diff 20001 символ → 413), OUT-1 (ответ содержит summary/risks≤3/checks), QA-1 (риск без evidence не попадает в ответ) |
| `tests_integration.md` | Связка `ReviewService` ↔ `/api/reviews` эндпоинт; связка `ReviewService` ↔ внешний LLM (в т.ч. таймаут по REL-1) |
| `tests_load.md` | Если нагрузочные данные не следуют из diff — явно обосновать отсрочку и указать условие, при котором тестирование понадобится (по разрешению `README.md`), а не оставлять пустым без причины |
| `tests_e2e.md` | Позитивный (валидный PR → структурированный ответ), негативный (diff > лимита → 413), граничный (LLM недоступен/таймаут → контролируемая ошибка) |
| `prompts.md` | Строка `P1-02` заполнена (инструмент/модель, ссылка на запрос, результат, что приняли/отклонили, как проверили); этот же `Master Prompt v1` вставлен в файл целиком; заполнена таблица «Сравнение двух запусков» по фактическому отличию P1-01 и P1-02 |

Каждый из 11 файлов должен также содержать заполненный раздел **«Как использовали AI»**: для чего, тип промпта = master prompt, строка в `prompts.md` (`P1-02`), что проверили и исправили сами.

### 4. Формат результата

- Не менять структуру, заголовки и таблицы существующих файлов — только заполнять пустые ячейки и разделы.
- Каждое утверждение о риске, проблеме или тесте подкреплено конкретной ссылкой `file:line` из diff или id правила (`SEC-1`, `API-1` и т.д.) — по духу `QA-1`.
- Таблицы остаются markdown-таблицами; диаграммы — валидный синтаксис mermaid (flowchart/sequenceDiagram/gantt).
- Если факта нет ни в diff, ни в `CASE.md`, ни в `README.md` — писать явно «неизвестно / требует уточнения от команды», а не придумывать цифры, даты, число пользователей или бизнес-метрики без пометки «гипотеза».
- Разделы по существу: таблицы и короткие пункты предпочтительнее длинных абзацев.

### 5. Полномочия и запреты

- **Разрешено:** читать `TRAINING_PR.diff` и перечисленные `.md`-файлы; заполнять и редактировать только 11 названных файлов; предлагать рефакторинг текстом (в ADR, тестах, плане), не кодом.
- **Запрещено:** approve или merge PR (`SCOPE-1`); писать или менять код в `app/*.py`; выполнять shell- или web-действия; выдумывать бизнес-факты (число пользователей, деньги, даты) без пометки «гипотеза»; включать в примеры и логи полное содержимое diff длиннее необходимого для иллюстрации (соблюдать дух `OBS-1` даже в документации).

### 6. Рабочий процесс и остановка

1. Прочитать `TRAINING_PR.diff` целиком.
2. Прочитать `CASE.md`, выписать релевантные правила в Context Pack, явно исключить нерелевантные (`snake_case`, i18n).
3. Заполнить `context.md`, затем `problem.md`, используя разрыв между diff и правилами как источник проблемы и метрик.
4. Заполнить `analysis.md` (AS IS по diff, TO BE — diff + внедрённые правила).
5. Заполнить `product_management.md` (use case, sequence diagram, позитивный и негативный/граничный сценарии).
6. Заполнить `project_management.md` (инкременты по правилам, роли человека/AI, Gantt).
7. Заполнить `adr.md` (решение, альтернативы, главный риск, схема).
8. Заполнить `tests_unit.md`, `tests_integration.md`, `tests_load.md`, `tests_e2e.md`, каждый тест — со ссылкой на правило или строку diff.
9. Заполнить `prompts.md`: строку `P1-02`, вставить этот Master Prompt v1 целиком, заполнить таблицу сравнения запусков.
10. В каждом из 11 файлов заполнить раздел «Как использовали AI».
- **Когда остановиться:** если для обязательного поля нет ни строки в diff, ни правила в `CASE.md`, ни данных в `README.md` — не придумывать значение, а пометить «требует уточнения у человека» и в конце ответа единым списком перечислить все такие открытые пункты.

### 7. Проверки и evidence

- Каждый риск, проблема или пункт use case — с точной ссылкой `path:line` из diff или id правила из `CASE.md`.
- Каждый тест — с конкретным воспроизводимым входом/действием/ожидаемым результатом (например: «отправить diff длиной 20 001 символ → ожидать HTTP 413», ссылка на `API-1`).
- Каждая mermaid-диаграмма — синтаксически валидна и соответствует реальному потоку из diff/ADR.
- По `QA-1`: если утверждение нельзя подтвердить строкой diff или правилом — не включать его как риск/факт, а вынести в «Что пока неизвестно» / «требует уточнения».

### 8. Definition of Done

- Во всех 11 файлах нет немотивированных пустых обязательных ячеек — только явно помеченные «неизвестно» / «не входит в задачу» с причиной.
- Каждый риск, тест и use case имеет evidence (`file:line` или id правила).
- Все mermaid-блоки синтаксически валидны.
- В `prompts.md` заполнены: строка `P1-02`, раздел `Master Prompt v1` (этим текстом), таблица сравнения двух запусков.
- В каждом из 11 файлов заполнен раздел «Как использовали AI».
- Список открытых вопросов «требует уточнения» вынесен отдельным перечнем в конце ответа.
