Findings (ordered by severity)
- app/api.py:35-38 (diff): No input validation. The handler accepts a plain dict and immediately indexes payload["diff"]. If the key is missing or not a string, this raises a 422/500 (KeyError becomes 500). Use a Pydantic model with a required diff: str and validate length.
- app/api.py:35-38 (diff): No authentication/authorization. Exposes an LLM-backed endpoint publicly. If this is not intentionally open, add auth or restrict access; otherwise this is a cost and abuse vector.
- app/review_service.py:19-22 (diff): No error handling around llm.generate. Any LLM/network failure will bubble up as a 500; no fallback or user-friendly error. Wrap and map to a controlled error response.
- app/review_service.py:19-22 (diff): Unbounded input size and runtime. The entire diff is inlined into the prompt without limits. Large diffs can cause excessive latency/costs or timeouts. Enforce a max size, chunking, or summarization and set a timeout/cancellation policy.
- app/api.py:35-38 (diff): Long-running synchronous work. The sync endpoint calls a potentially slow LLM in a threadpool; under load, this can exhaust the threadpool and degrade the app. Consider making the path async and offloading to an async LLM client or run_in_executor with concurrency limits/queueing.
- app/api.py:35-38 (diff): Weak contract in OpenAPI. payload: dict produces a very loose schema (arbitrary object), making client generation and docs poor. Define request and response models to lock the schema.
- app/review_service.py:19-22 (diff): Response shape is underspecified and inflexible. The service returns {"comment": str} only. If clients need structured findings (e.g., list of issues with severity/locations), this design will require breaking changes. Consider returning a typed structure from the start.
- Compatibility risk: Using PEP 585 generics dict[str, str] requires Python 3.9+. If the project targets 3.8, imports will fail. Confirm runtime; otherwise use Dict[str, str] from typing.
- Internationalization consistency: Prompt is English (“Review this pull request…”), while the project context appears Russian. Align language expectations or make it configurable.
- Observability: No logging/metrics around LLM requests (latency, tokens, errors). Hard to operate and debug in production.
- Minor style consistency: In LLM Protocol the method now uses a multi-line body with ... on the next line. Functionally fine but inconsistent with the prior style; consider keeping a single-line stub or add @runtime_checkable if you expect isinstance checks.
Open questions
- What Python version is the target runtime? If <3.9, the dict[str, str] annotations will break imports.
- Is this endpoint intended to be public? If not, what auth mechanism should be used?
- What is the expected response contract for reviews? Do you need structured issues (with file/line/severity), or is a single free-form comment acceptable for now?
- Are there size limits or SLAs for diffs and response times? This affects truncation, chunking, and timeout choices.
- Do we have an async-capable LLM client, or should we run sync calls in a bounded executor?
