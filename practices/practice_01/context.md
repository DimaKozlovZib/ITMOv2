## Context Pack для первого рабочего сценария

### Факты и правила

- Задача помощника: для одного PR вернуть `summary`, ≤3 `risks[file,line,evidence,risk]` и `checks`; решение принимает человек (CASE.md).
- SEC‑1: перед отправкой во внешний LLM из diff удаляются токены/пароли/ключи.
- API‑1: diff > 20 000 символов отклоняется с HTTP 413.
- REL‑1: внешний LLM‑вызов имеет timeout 10 сек; ошибка превращается в контролируемый ответ.
- OUT‑1: ответ содержит `summary`, массив `risks` и массив `checks` (до 3 рисков), поля `file`, `line`, `evidence`, `risk` обязательны.
- SCOPE‑1: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- QA‑1: риск включается в ответ только при подтверждении строкой diff или правилом.
- OBS‑1: в лог пишутся только `request_id`, длительность и статус; содержимое diff/ответа не логируется.

### Формат входа и результата

- Вход: JSON `{"diff": "..."}` в POST /api/reviews (app/api.py:8‑10).
- Результат AS IS: `{"comment": str}` (app/review_service.py:16) — не соответствует OUT‑1.

### Ограничения и запрещённые действия

- Нельзя approve/merge, менять код в GitHub; сервис только советует (SCOPE‑1, CASE.md).
- Нельзя отправлять секреты во внешний LLM (SEC‑1).
- Длинные diff (>20 000 символов) должны быть отклонены (API‑1).

### Хороший пример

```
app/review_service.py:14 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC‑1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```

### Плохой пример

```
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Что пока неизвестно

- Логирование (OBS‑1): нет явного логирования в коде — требуется уточнение.
- Реализация зависимостей (`app.dependencies.review_service`) — недоступна в diff.
- Точное форматирование и контракты ответа целевого сервиса — требуется уточнение.
