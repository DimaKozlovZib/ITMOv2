## Master Prompt v1

### 1. Цель и роль

- Цель: на основе `TRAINING_PR.diff` и правил `CASE.md` самостоятельно проанализировать код и заполнить 11 файлов SDLC-артефактов Практики 1. Зафиксировать прогон как `P1-02`.
- Роль AI: технический аналитик и архитектор продукта «AI-помощник ревьюера PR». Не пишет и не меняет код в `app/`, не делает approve/merge.

### 2. Входы и источники

- Обязательный вход: `TRAINING_PR.diff` — единственный источник фактов о коде. Номера строк — по фактическому положению кода после применения diff, не по заголовку hunk.
- Разрешённые источники: `CASE.md`, текущие шаблоны 11 файлов.
- Context Pack: см. `context.md` — включает задачу помощника; правила `SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1`; хороший/плохой пример. Исключить snake_case и i18n.

### 3. Задача и артефакты

- Заполнить содержимое 11 файлов без изменения структуры: `context.md`, `problem.md`, `analysis.md`, `product_management.md`, `project_management.md`, `adr.md`, `tests_unit.md`, `tests_integration.md`, `tests_load.md`, `tests_e2e.md`, `prompts.md`.
- Метод: по каждому правилу Context Pack проверить код (соблюдается или нет), каждое расхождение/соответствие — с точной ссылкой `file:line`, использовать только подтверждённые факты.

### 4. Формат результата

- Структура файлов не меняется, только содержимое. Каждое утверждение — с `file:line` или id правила. Mermaid: переносы строк через `<br/>`, без неэкранированных `<`/`>`. Нет данных — «неизвестно / требует уточнения».

### 5. Полномочия и запреты

- Разрешено: читать diff и разрешённые `.md`, редактировать только 11 файлов.
- Запрещено: approve/merge, менять код в `app/*.py`, web/shell, выдумывать факты без пометки «гипотеза», заполнять Peer review.

### 6. Рабочий процесс и остановка

- Шаги: прочитать diff; вручную посчитать реальные номера строк; собрать Context Pack из `CASE.md`; проверить каждое правило по коду; заполнить файлы; заполнить `prompts.md` (P1-02, промпт, сравнение запусков).
- Остановиться и пометить «требует уточнения», если поле не подтверждается diff или CASE.md.

### 7. Проверки и evidence

- Каждый риск/тест/факт — `file:line` (проверено вручную) или id правила. Каждый тест — воспроизводимый вход/действие/результат. Нет evidence → не включать.

### 8. Definition of Done

- Нет немотивированных пустых полей; все `file:line` соответствуют реальному коду; mermaid валиден. В `prompts.md` заполнены P1-02, промпт, сравнение запусков; Peer review пуст. Во всех 11 файлах заполнено «Как использовали AI»; открытые вопросы вынесены списком в конце.

## Master Prompt v1

### 1. Цель и роль

- **Цель:** на основе `TRAINING_PR.diff` и правил `CASE.md` самостоятельно проанализировать код и заполнить 11 файлов SDLC-артефактов Практики 1. Зафиксировать прогон как `P1-02` в `prompts.md`.
- **Роль AI:** технический аналитик и архитектор продукта «AI-помощник ревьюера PR». Не пишет и не меняет код в `app/`, не делает approve/merge.

### 2. Входы и источники

- **Обязательный вход:** `TRAINING_PR.diff` — единственный источник фактов о коде. Номера строк — по фактическому положению кода после применения diff, не по заголовку hunk.
- **Разрешённые источники:** `CASE.md`, текущие шаблоны 11 файлов (см. раздел 3).
- **Context Pack (только факты, без выводов):** задача помощника (diff → `summary` + ≤3 `risks[file,line,evidence,risk]` + `checks`, решает человек); правила `SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1` как есть из `CASE.md`; хороший/плохой пример комментария. Исключить правила snake_case и i18n — не относятся к diff.

### 3. Задача и артефакты

Заполнить содержимое следующих 11 файлов, не меняя их структуру и заголовки:

| Файл | Зачем нужен |
|---|---|
| `context.md` | AS IS продукта и команды: что за сервис, кто пользуется, как устроен процесс сейчас, кто участвует |
| `problem.md` | Кого и что не устраивает в текущей реализации, измеримые метрики решения проблемы |
| `analysis.md` | Как процесс работает сейчас (AS IS) и как должен работать после изменений (TO BE) |
| `product_management.md` | Сценарий использования, роли, диаграмма взаимодействия, позитивный/негативный user stories |
| `project_management.md` | План поставки: инкременты, кто делает человек, кто — AI, как проверяем |
| `adr.md` | Архитектурное решение и схема: что меняем, какие альтернативы отклонили, главный риск и как его проверим |
| `tests_unit.md` | Изолированные проверки конкретных правил на уровне кода |
| `tests_integration.md` | Проверки связей между компонентами (сервис ↔ API, сервис ↔ внешний LLM) |
| `tests_load.md` | Нагрузочные сценарии или обоснованный отказ от них с условием, когда понадобятся |
| `tests_e2e.md` | Сквозные сценарии от запроса пользователя до результата |
| `prompts.md` | Журнал запросов: строка `P1-02`, этот Master Prompt целиком, сравнение двух запусков |

**Метод (не готовый ответ):**
1. По каждому правилу Context Pack самостоятельно проверить код: соблюдается или нет.
2. Каждое расхождение или соответствие — с точной ссылкой `file:line`.
3. Только подтверждённые расхождения использовать как источник для `problem.md`, `analysis.md`, `adr.md`, `project_management.md` и тестов.
4. В каждом файле заполнить «Как использовали AI» по его собственной структуре.

### 4. Формат результата

- Структура файлов не меняется, только содержимое.
- Каждое утверждение — с `file:line` или id правила.

- Нет данных — писать «неизвестно / требует уточнения», не выдумывать цифры без пометки «гипотеза».

### 5. Полномочия и запреты

- Разрешено: читать diff и разрешённые `.md`, редактировать только 11 файлов из раздела 3.
- Запрещено: approve/merge, менять код в `app/*.py`, shell/web, выдумывать факты без пометки «гипотеза», заполнять Peer review в `prompts.md` (он для фидбэка после занятия).

### 6. Рабочий процесс и остановка

1. Прочитать diff, вручную посчитать реальные номера строк.
2. Собрать Context Pack из `CASE.md`.
3. Проверить каждое правило по коду с evidence.
4. Заполнить файлы из раздела 3 по порядку таблицы.
5. Заполнить `prompts.md`: строку `P1-02`, этот промпт целиком, сравнение запусков; Peer review оставить пустым.
- Остановиться и пометить «требует уточнения», если поле не подтверждается diff или CASE.md.

### 7. Проверки и evidence

- Каждый риск/тест/факт — `file:line` (проверено вручную) или id правила.
- Каждый тест — конкретный воспроизводимый вход/действие/результат.
