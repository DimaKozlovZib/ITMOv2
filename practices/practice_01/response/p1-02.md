## Context Pack для первого рабочего сценария

### Факты и правила

- Стек и соглашения, выводимые из diff: Python 3 (type hints PEP 585), FastAPI, протокол `LLM` (PEP 544), разделение на слой API и сервис.
- Репозитории правил, влияющие на задачу (см. [`CASE.md`](CASE.md)):
  - `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
  - `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
  - `REL-1`: внешний LLM‑вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
  - `OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`. В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.
  - `SCOPE-1`: сервис только советует; он не пишет код и не выполняет действия в GitHub.
  - `QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
  - `OBS-1`: в лог пишутся только `request_id`, длительность и статус. Содержимое diff и ответа модели не логируется.

### Формат входа и результата

- Вход: строка `diff` в теле запроса `POST /api/reviews`.
- Результат: объект с полями `summary`, `risks[<=3]`, `checks` (см. `OUT-1`).

### Ограничения и запрещённые действия

- Не отправлять секреты во внешний LLM (`SEC-1`).
- Отклонять слишком длинные diff с 413 (`API-1`).
- Не approve/merge и не менять код (`SCOPE-1`).

### Хороший пример

app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов, что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться, что в prompt осталось [REDACTED].

### Плохой пример

Код можно улучшить. Добавьте тесты и обработку ошибок.

### Что пока неизвестно

- Аутентификация/авторизация API; схема логирования и трассировки; реализация `app.dependencies`; механизм редакции секретов; лимиты RPS и квоты LLM.

# Проблема и метрики

## Проблема

- Пользователь: инженер‑ревьюер, использующий AI‑помощника для первичного анализа PR.
- Ситуация: в сервис добавлен endpoint `POST /api/reviews`, который принимает `diff` и проксирует его во внешний LLM через `ReviewService`.
- Что происходит сейчас: по diff видно, что нет валидации длины входа, удаления секретов, таймаутов и унифицированного формата ответа; API возвращает `dict[str, str]` с полем `comment`, что расходится с `OUT-1`.
- Почему это мешает пользователю или бизнесу: повышенные риски утечки секретов и нестабильного поведения (таймауты/ошибки), трудно использовать результат автоматически из‑за несоответствия контракту ответа.
- Что не входит в задачу: интеграция с GitHub, автоматическое принятие решений, изменение чужих систем; любые изменения вне `diff`.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля запросов с ответом, соответствующим `OUT-1` | 0% по текущему коду (возвращается `comment`) | 100% | На каждом релизе | Авто‑тест формы ответа |
| Таймаут запроса к LLM | Не определено из diff | ≤ 10 секунд | Во время интеграционного теста | Конфиг сервиса / моки |
| Доля отклонённых слишком длинных diff | Не определено из diff | 100% для >20k символов | Нагрузочный тест | API‑слой |

## Почему изменение метрики подтвердит решение проблемы

Соответствие `OUT-1` позволяет подключать автоматические проверки и консюмеров API. Таймаут и ограничение размера diff снижают нестабильность и издержки, соответствуют правилам `REL-1` и `API-1`.
